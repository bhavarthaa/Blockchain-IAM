# Node.js/TypeScript REST API Specification

## 1. Scope and architectural rules

The backend is a modular Node.js/TypeScript service. It exposes REST endpoints for the Next.js frontend and public verification clients, owns SIWE authentication, performs authorization pre-checks, submits blockchain transactions, serves PostgreSQL projections, and runs the blockchain event indexer.

The API is not the authority for blockchain state. Smart contracts remain authoritative for identity status, permissions, ownership, transaction success, and immutable audit events. PostgreSQL is a derived read model and operational store.

### 1.1 Operation classes

Every endpoint belongs to one of these classes:

| Class | Behavior | Source of truth |
|---|---|---|
| Database read | Queries Prisma projections; returns freshness metadata | PostgreSQL projection, with optional chain reconciliation |
| Blockchain transaction | Validates/authenticates, pre-checks permission, submits a transaction, returns operation status | Smart contract and canonical receipt |
| Authentication | Issues/consumes SIWE nonces and sessions | Wallet signature plus backend session store |
| Indexing/operations | Runs or inspects event ingestion and checkpoints | Blockchain logs plus indexer state |
| Public verification | Reads projections and direct contracts when proof/freshness matters | Direct chain read for authoritative fields |

### 1.2 Common request headers

- `Authorization: Bearer <access-token>` for authenticated routes.
- `Idempotency-Key: <client-generated-unique-key>` for every write endpoint.
- `X-Chain-Id: <numeric-chain-id>` when the request is chain-specific.
- `X-Request-Id: <trace-id>` generated by the client or assigned by the API.

### 1.3 Common response envelope

Successful responses use:

```json
{
  "data": {},
  "meta": {
    "requestId": "req_01...",
    "chainId": 31337,
    "lastIndexedBlock": "120",
    "freshness": "indexed"
  }
}
```

Write responses use `202 Accepted` while a transaction is pending:

```json
{
  "data": {
    "operationId": "op_01...",
    "transactionId": "db_01...",
    "txHash": "0x...",
    "status": "SUBMITTED",
    "statusUrl": "/api/v1/transactions/0x..."
  }
}
```

### 1.4 Common error format

```json
{
  "error": {
    "code": "INSUFFICIENT_PERMISSION",
    "message": "The wallet does not have ASSET_MINT permission.",
    "details": {},
    "requestId": "req_01..."
  }
}
```

Standard status meanings:

- `400` malformed or semantically invalid request.
- `401` missing, expired, invalid, or mismatched wallet session.
- `403` authenticated wallet lacks the required permission.
- `404` projection or requested resource does not exist.
- `409` duplicate/idempotency conflict or stale version conflict.
- `422` valid JSON but invalid domain input.
- `429` rate limit exceeded.
- `502` upstream RPC/IPFS/provider failure.
- `503` database, indexer, or blockchain dependency unavailable.

```text

```

### Module responsibilities

| Module | Responsibility |
|---|---|
| `auth` | SIWE nonce lifecycle, signature verification, session/JWT issuance and revocation |
| `identities` | Identity projection reads and identity lifecycle transaction orchestration |
| `roles` | Role assignments and role projection reads |
| `permissions` | Permission catalog and on-chain permission pre-checks |
| `assets` | Asset metadata, minting, assignment, metadata update, and burn orchestration |
| `ownership` | Current owner and transfer history queries; transfer authorization |
| `verification` | Public DID, asset, ownership, and proof freshness checks |
| `audit` | Indexed audit timeline and export authorization |
| `transactions` | Idempotent operation records, receipt polling, confirmation/failure status |
| `indexing` | Block/log ingestion, checkpointing, replay, reorg handling, and indexer health |
| `blockchain` | Read/write RPC clients, ABI calls, revert decoding, chain configuration |
| `database` | Prisma client, repositories, transaction boundaries, and projection queries |

Controllers parse HTTP input and select a response status. Services enforce domain rules and coordinate dependencies. Repositories perform Prisma reads/writes. The blockchain service is the only module allowed to submit contract transactions.

## 3. Authentication endpoints

### `POST /api/v1/auth/nonce`

| Field | Specification |
|---|---|
| Authentication | None; rate-limited by IP and address |
| Required role/permission | None |
| Request body | `{ "address": "0x...", "chainId": 31337 }` |
| Validation | Checks a normalized EVM address, supported chain ID, and nonce request rate. The server generates the nonce; a client-supplied nonce is ignored. |
| Response | `200` with `{ nonce, domain, uri, chainId, issuedAt, expirationTime }` |
| Errors | `400` invalid address/chain; `429` rate limit; `503` session store unavailable |
| Blockchain interaction | None |

Creates a one-time nonce bound to address, domain, URI, chain ID, and expiry. It is consumed atomically by the SIWE verification endpoint.

### `POST /api/v1/auth/siwe`

| Field | Specification |
|---|---|
| Authentication | None; signature proves wallet control |
| Required role/permission | None |
| Request body | `{ "message": "<EIP-4361 SIWE message>", "signature": "0x..." }` |
| Validation | Parses SIWE, verifies domain/URI, chain ID, nonce, issued/expiration times, statement policy, signature, and recovered address. Consumes the nonce exactly once. |
| Response | `200` with short-lived access token, expiry, wallet, chain ID, DID if indexed, and role snapshot |
| Errors | `400` malformed message; `401` invalid signature, nonce, domain, chain, or expiry; `409` nonce already consumed; `503` session store unavailable |
| Blockchain interaction | Direct read of `IdentityRegistry`/`RoleManager` may enrich the session role snapshot. No write. |

SIWE authenticates wallet control. It does not grant a role or permission.

### `POST /api/v1/auth/logout`

| Field | Specification |
|---|---|
| Authentication | Required |
| Required role/permission | Any authenticated session |
| Request body | Empty; token is identified by the bearer credential |
| Validation | Validates token and revokes the session identifier |
| Response | `204 No Content` |
| Errors | `401` invalid/expired token; `503` session store failure |
| Blockchain interaction | None |

### Indexer processing contract

The indexer is a worker, not a request handler:

1. Loads `IndexerCheckpoint`.
2. Reads canonical logs from the deployment block or next checkpoint.
3. Inserts `BlockchainTransaction` and `IndexedEvent` rows using unique event provenance.
4. Upserts identity, role, asset, ownership, and audit projections in one Prisma transaction.
5. Advances the checkpoint only after all projection writes commit.
6. Publishes WebSocket invalidation events after commit.
7. Detects block-hash divergence, rolls back orphaned derived rows, and replays from the common ancestor.

## 12. Authorization pipeline

Every authenticated write passes the following layers:

1. **Transport:** HTTPS, CORS, body size, rate limit, and request ID.
2. **Authentication:** verify the short-lived SIWE session and recover the wallet address.
3. **Input validation:** validate schemas before database or RPC calls.
4. **Policy pre-check:** call `RoleManager.hasPermission`, resolve active DID/ownership, and reject obvious `403` requests.
5. **Transaction construction:** only the transaction service builds the contract call; it binds the authenticated wallet/actor to the operation.
6. **On-chain enforcement:** the contract checks `msg.sender`, roles, permissions, active identities, ownership, and paused state again.
7. **Projection:** indexer derives final application state only from canonical logs and receipts.

PostgreSQL role or ownership rows may improve UX but cannot grant permission. If the database projection is stale, direct contract reads take precedence.

## 13. Read-only database operations versus blockchain operations

### Read-only database operations

`GET /identities`, `GET /roles`, `GET /permissions`, `GET /assets`, ownership history, normal audit queries, transaction status from indexed data, and dashboard queries use Prisma repositories. Responses include `lastIndexedBlock` and freshness state. They do not mutate the chain.

### Blockchain transactions

Identity creation/update/revoke/restore, role assignment/revocation, permission configuration, mint, assignment, transfer, metadata update, and burn pass through the transaction service. The API records an operation, submits a signed user or relayer transaction, returns `202`, and waits for receipts/indexing. It never writes a successful projected state optimistically.

### Authentication

Nonce and SIWE endpoints prove wallet control and issue/revoke API sessions. A valid session is not a role.

### Authorization

The backend performs a direct on-chain permission pre-check and contract calls are the final enforcement boundary. Frontend visibility and database role rows are not security controls.

### Blockchain event indexing

The indexer is the only writer of chain-derived projection state. It consumes logs, deduplicates by chain/transaction/log index, handles confirmations and reorgs, and updates PostgreSQL inside checkpointed transactions.

## 14. Cross-cutting controls

- Validate all input with a schema library such as Zod and reject unknown properties on writes.
- Normalize addresses and bytes32 values before authorization or persistence.
- Require idempotency keys on every state-changing route.
- Apply per-IP and per-wallet rate limits, with stricter limits on nonce and transaction endpoints.
- Use structured errors; never expose private keys, RPC credentials, database URLs, or raw provider secrets.
- Decode known contract custom errors into stable API error codes; preserve the transaction hash for unknown failures.
- Use timeouts and bounded retries for RPC and database operations. Do not blindly resubmit an ambiguous transaction.
- Log request ID, authenticated wallet, route, operation ID, tx hash, and outcome; do not log SIWE signatures or sensitive payloads.
- Configure CORS to the deployed frontend origin and enforce HTTPS outside local development.
- Return only public/anonymized fields from verification and audit routes according to the privacy policy.
- Use WebSocket notifications only as cache invalidation hints; clients refetch authoritative API data.
